# راهنمای عملیاتی آزمون آینده‌نگر ChartAnalyzer

این راهنما برای اجرای Prospective Holdout روی نسخه تثبیت‌شده ChartAnalyzer است. این آزمون پیش‌بینی‌های PMI را روی داده‌ای که پس از ثبت و Freeze مدل جمع‌آوری می‌شود ارزیابی می‌کند. این آزمون به‌تنهایی سودآوری یک استراتژی معاملاتی یا آمادگی اجرای سفارش را اثبات نمی‌کند.

## 1. پیش‌نیازها

- نسخه‌ای از main که تمام CIهای مسدودکننده آن سبز است.
- اجرای محلی API روی loopback؛ در مثال‌ها مقدار $Base را با آدرس واقعی سرور تنظیم کنید.
- پیکربندی بازار روی spot؛ Futures در این پروتکل فعلاً پشتیبانی نمی‌شود.
- دسترسی پایدار به منبع داده انتخاب‌شده.
- زمان سیستم Windows همگام باشد.
- پیش از ثبت cohort، نسخه کد و تنظیمات را تثبیت کنید. هویت cohort شامل SHA-256 اجزای کد و تنظیمات است؛ تغییر کد در میانه آزمون باعث رد درخواست‌های بعدی می‌شود.

## 2. طراحی نمونه پیشنهادی

نمونه آغازین برای BTC:

| پارامتر | مقدار |
|---|---:|
| Symbol | BTCUSDT |
| Timeframe | 1h |
| Forecast horizon | 4 bars |
| History bars | 1200 |
| Bootstrap paths | 3000 |
| Minimum forecasts | 200 |
| Minimum segment count | 30 |
| Collection duration | 42 days |

به دلیل سیاست عدم هم‌پوشانی، پیش‌بینی جدید تا سررسید افق قبلی صادر نمی‌شود. برای افق 4 کندل یک‌ساعته و 200 پیش‌بینی، حداقل نظری حدود 796 ساعت است. 42 روز تقریباً 1008 ساعت فراهم می‌کند و حاشیه‌ای برای تأخیر یا کندل‌های ازدست‌رفته می‌گذارد.

این اعداد باید پیش از شروع ثبت شوند و در طول آزمون تغییر نکنند.

## 3. ثبت cohort آینده‌نگر

نمونه PowerShell زیر زمان شروع را پنج دقیقه در آینده و پایان را 42 روز بعد تعیین می‌کند. آن را با آدرس واقعی API اجرا کنید:

~~~powershell
$Base = "http://127.0.0.1:8765"
$Start = [DateTimeOffset]::UtcNow.AddMinutes(5)
$End = $Start.AddDays(42)

$Payload = @{
    cohort_id = "BTCUSDT-SPOT-1H-H4-PROSPECTIVE-01"
    source = "ccxt"
    exchange = "binance"
    symbol = "BTC/USDT"
    tf = "1h"
    horizon_bars = 4
    paths = 3000
    n = 1200
    collection_start = $Start.ToString("o")
    collection_end = $End.ToString("o")
    min_forecasts = 200
    min_segment_count = 30
}

$Json = $Payload | ConvertTo-Json -Depth 8
$Registration = Invoke-RestMethod -Method Post -Uri "$Base/api/prospective-holdout/register" -ContentType "application/json" -Body $Json
$Registration | ConvertTo-Json -Depth 12
~~~

اگر منبع CCXT در محیط اجرا قابل دسترسی نیست، می‌توان از Ramzinex استفاده کرد؛ اما انتخاب منبع باید پیش از ثبت انجام شود. در طول cohort منبع، نماد، تایم‌فریم، افق، تعداد کندل‌های ورودی، تعداد مسیرها و نسخه مدل را عوض نکنید. فرمت نماد باید مطابق قرارداد منبع انتخابی باشد.

پاسخ ثبت باید شامل SCHEDULED، اثرانگشت پیکربندی و هویت مدل باشد. این اطلاعات را در پرونده آزمایش ذخیره کنید.

## 4. اجرای دوره‌ای tick

پس از رسیدن زمان شروع، endpoint زیر باید به‌صورت دوره‌ای فراخوانی شود:

~~~powershell
$TickPayload = $Payload.Clone()
$TickJson = $TickPayload | ConvertTo-Json -Depth 8

Invoke-RestMethod -Method Post -Uri "$Base/api/prospective-holdout/tick" -ContentType "application/json" -Body $TickJson | ConvertTo-Json -Depth 12
~~~

برای شروع، هر 5 دقیقه یک بار فراخوانی کافی است؛ پیش‌بینی جدید فقط وقتی صادر می‌شود که زمان آن رسیده باشد و داده کندل بسته‌شده جدید در دسترس باشد. می‌توان این دستور را با Windows Task Scheduler زمان‌بندی کرد.

هر پاسخ را ثبت کنید. مهم‌ترین فیلدها:

- issued_forecast: شناسه و زمان صدور پیش‌بینی جدید؛ ممکن است null باشد.
- resolved_this_tick: تعداد نتایج سررسیدشده‌ای که این نوبت حل شدند.
- unresolved_due: نتایجی که به دلیل نبود داده معتبر هنوز حل نشده‌اند.
- report_available: تا پایان بازه و ارزیابی یک‌باره باید false بماند.

خطا یا داده نامعتبر را با تغییر پارامترها دور نزنید. داده ناقص باید رد یا unresolved باقی بماند؛ این رفتار بخشی از اعتبار آزمون است.

## 5. پایش بدون افشای امتیاز

برای مشاهده وضعیت:

~~~powershell
$Cohort = "BTCUSDT-SPOT-1H-H4-PROSPECTIVE-01"
Invoke-RestMethod -Method Get -Uri "$Base/api/prospective-holdout/status?cohort_id=$Cohort" | ConvertTo-Json -Depth 12
~~~

وضعیت می‌تواند تعداد پیش‌بینی‌ها، تعداد نتایج حل‌شده و سلامت زنجیره رویداد را نشان دهد، اما تا زمان ارزیابی نباید امتیاز عملکرد را افشا کند.

## 6. ارزیابی نهایی یک‌باره

فقط وقتی تمام شرایط زیر برقرار است ارزیابی را اجرا کنید:

1. زمان collection_end گذشته باشد.
2. حداقل تعداد پیش‌بینی ثبت شده باشد.
3. تمام پیش‌بینی‌ها نتیجه معتبر داشته باشند.
4. verify_integrity وضعیت PASS بدهد.
5. مدل، کد و پیکربندی در طول آزمون ثابت مانده باشند.

سپس:

~~~powershell
$Final = Invoke-RestMethod -Method Post -Uri "$Base/api/prospective-holdout/evaluate" -ContentType "application/json" -Body (@{ cohort_id = $Cohort } | ConvertTo-Json)
$Final | ConvertTo-Json -Depth 30
~~~

گزارش نهایی یک‌بار ساخته و ذخیره می‌شود. endpoint ارزیابی مجدد را رد می‌کند.

## 7. تفسیر گزارش

گزارش شامل خطاهای پیش‌بینی، پوشش بازه پیش‌بینی، Pinball Loss، کالیبراسیون در صورت وجود احتمال جهت، تفکیک رژیم‌ها و مقایسه جفت‌شده با سه baseline از پیش ثبت‌شده است:

- بازده صفر
- توزیع تاریخی بدون شرط
- نوسان EWMA با توزیع گاوسی

برای معیارهای خطا، مقدار کمتر بهتر است. در مقایسه candidate-minus-baseline، مقدار منفی به نفع مدل است. پوشش بالاتر به‌تنهایی کافی نیست؛ بازه بسیار عریض می‌تواند پوشش را بالا ببرد، بنابراین پوشش باید همراه با عرض بازه و Pinball Loss تفسیر شود.

اگر بازه اطمینان اختلاف خطا با baseline صفر را قطع کند، شواهد برتری قطعی وجود ندارد. نمونه کوچک یا بخش‌هایی با تعداد کم باید «نامشخص» گزارش شوند، نه موفق.

## 8. محدودیت‌هایی که نباید پنهان شوند

- این cohort فعلی برای دقت پیش‌بینی توزیعی PMI است، نه آزمون مستقیم سود و زیان معاملات.
- ورودی و نتیجه در پیاده‌سازی فعلی از همان provider انتخاب‌شده دریافت می‌شوند؛ این جداسازی زمانی است، نه تأیید مستقل چند صرافی.
- زنجیره hash دست‌کاری تصادفی یا تغییر payload را آشکار می‌کند، اما در برابر مدیری که به فایل SQLite دسترسی کامل دارد و می‌تواند زنجیره را دوباره بسازد، سامانه tamper-proof محسوب نمی‌شود.
- tickها باید روی ماشینی اجرا شوند که به API و منبع داده دسترسی دارد. توقف طولانی collector ممکن است cohort را از حداقل تعداد نمونه پایین‌تر بیاورد.
- تغییر کد یا تنظیمات در میانه آزمون مجاز نیست. برای نسخه جدید باید cohort تازه‌ای با شناسه و دیتابیس جدید ثبت شود.
- موفقیت در این آزمون به معنی edge معاملاتی اثبات‌شده نیست. برای آن، یک پروتکل جداگانه با اجرای شبیه‌سازی‌شده واقع‌گرایانه، هزینه‌های معامله، مقایسه با baselineهای معاملاتی و سپس Paper Trading لازم است.

## 9. معیار پایان

آزمون فقط وقتی قابل گزارش است که حداقل نمونه از پیش ثبت‌شده، پوشش کامل نتایج، سلامت زنجیره و گزارش baselineها موجود باشند. نتیجه منفی یا نامشخص هم نتیجه معتبر تحقیق است؛ cohort را برای بهتر نشان‌دادن مدل حذف یا دوباره‌تنظیم نکنید.
